## 2. Commit `6ca148b` — Login Lockout (R5-59 §12)

### 2.1 Findings — lockout correctness & bypass

**Q: Can the counter be bypassed by e-mail case/whitespace/unicode variants?**
No. `AuthService.LoginAsync` normalises once — `(request.Email ?? string.Empty).Trim().ToLowerInvariant()` (`Application/Services/Implementation/AuthService.cs:239`) — and passes that **same string** to every limiter call and to the DB lookup `u.Email == emailNormalized` (`AuthService.cs:260`). The limiter re-normalises defensively with the identical rule (`Infrastructure/Auth/LoginAttemptLimiter.cs:117-120`). Since both keys derive from one local, there is no input for which the limiter key and the lookup key diverge. Unicode that .NET case-folds to the same lowercase (e.g. U+212A KELVIN SIGN → `k`) folds **identically in both places**, so it shares the counter rather than bypassing it. Whitespace is trimmed on both. ✅ No bypass. (Note: other `Async` login paths — invite/magic-link/API-key — don't record failures, by design per §12; they are token-brute-force surfaces with 256-bit tokens, not password surfaces.)

**Q: Does an unknown e-mail count (no enumeration difference)?**
Yes. `user == null || !Verify(...)` records a failure identically (`AuthService.cs:266-270`), and the `PasswordlessOnly` explicit refusal also counts (`AuthService.cs:277-281`). Lockout for `doesnotexist@x` behaves the same as for a real address, so the 429 leaks nothing about account existence. ✅

**Q: Is the 429 path free of timing/enumeration leaks vs 400?**
The 429 short-circuits before the DB and before BCrypt (`AuthService.cs:242-250`), so it is strictly faster than a 400. What that timing difference reveals is only *lock state of the submitted address* — which the caller created themselves (they made the 10 failures), not account existence. Acceptable. ⚠️ **Pre-existing, adjacent:** the `user == null || Verify` short-circuit means unknown e-mail (no BCrypt, ~1 ms) vs wrong password (BCrypt, ~100–300 ms) is itself a user-existence oracle — older than this commit, but this commit built a wall next to it. Follow-up F3.

**Q: Is the IMemoryCache entry bounded (sliding vs absolute; memory growth under e-mail spray)?**
Per-entry: yes. Each failure sets an **absolute** expiry `entry.LockedUntil ?? now + window` (`LoginAttemptLimiter.cs:100-101`) — refreshed per failure, so failures must keep arriving within 15 min of each other to accumulate (effectively a sliding *accumulation* window, which is the correct semantic). Once locked, the entry dies at `LockedUntil` and `IsLockedAsync` removes it on expiry (`LoginAttemptLimiter.cs:43-51`). Concurrent in-flight requests that both passed `IsLockedAsync` cannot extend the lock — the second `RecordFailureAsync` sees `LockedUntil` already set and leaves it (`LoginAttemptLimiter.cs:95-98`). ✅ per entry.

Aggregate: ❌ **NOT bounded — this is the must-fix.** `IMemoryCache` is registered with default options (`API/Extensions/AuthenticationExtensions.cs:35`, `Infrastructure/DependencyInjection.cs:33`) — no `SizeLimit`, so the cache never trims under pressure. Entry count is bounded by spray volume (one entry per distinct e-mail, TTL ≤ 15 min; the per-IP floor `login-ip` caps insertion at 60/min/IP — `API/Extensions/RateLimitingExtensions.cs:136-144`), but **entry SIZE is unbounded** because `LoginValidator` applies `NotEmpty().EmailAddress()` with **no `MaximumLength`** (`Application/Validators/LoginValidator.cs:10-12`) and `AuthController.Login` has no `[RequestSizeLimit]`. Kestrel's default body limit is 30 MB; a ~10 MB syntactically-valid e-mail passes validation, fails the lookup, and is stored **verbatim as the cache key** (`LoginAttemptLimiter.cs:120`). Steady state from a single anonymous IP: 60 inserts/min × 15-min TTL × attacker-chosen size ≈ **9 GB at 10 MB per e-mail** — OOM. Distributed sources scale linearly.

**Fix (concrete):**
1. `Application/Validators/LoginValidator.cs:10` → `.NotEmpty().EmailAddress().MaximumLength(254);` (matches `CreateTenantInviteValidator.cs:10`; RFC max is 254/320).
2. Hardening in `LoginAttemptLimiter.CacheKey` (`LoginAttemptLimiter.cs:120`): key on `Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(NormalizeEmail(email))))` — fixed 64-char key regardless of input, making the cache's memory per e-mail constant.
3. Optionally `[RequestSizeLimit(64 * 1024)]` on `AuthController.Login` — the login body is two short strings.

**Q: Does a successful login reset the counter BEFORE issuing the token?**
Yes. `ResetAsync` at `AuthService.cs:302` precedes `_tokenService.Issue(user)` at `:304`, and runs only after password verification *and* the Pending/Rejected/Disabled gates — so a Pending account's successful password does not reset its own failure counter (correct: status failures aren't password failures, but see note — they also don't *record* failures, which is fine since the password was proven). ✅

**Q: Is `Retry-After` computed from the real remaining window?**
Yes. `GetRetryAfterSecondsAsync` returns `ceil(LockedUntil − now)`, clamped ≥ 1 (`LoginAttemptLimiter.cs:69-71`), and the controller writes it as a seconds-form `Retry-After` (`API/Controllers/AuthController.cs:30-33`) — matching the framework limiter's own convention (`RateLimitingExtensions.cs:34-36`). Minor TOCTOU: if the lock expires between `IsLockedAsync` and `GetRetryAfterSecondsAsync` (two separate calls, `AuthService.cs:242-244`), the client gets 429 with `Retry-After: 0` — cosmetic, self-corrects on retry. (Folding the two limiter calls into one `TryGetLockout(email, out remaining)` would remove it.)

**Q: Does the per-IP `login-ip` floor use the forwarded client IP behind Caddy?**
Order is correct: `UseForwardedHeaders` at `API/Program.cs:191-197`, `UseRateLimiter()` at `:381`, and `ClientIp` reads `Connection.RemoteIpAddress` (`RateLimitingExtensions.cs:42-43`), which the forwarded-headers middleware rewrites — so the floor partitions on the address Caddy forwarded, and the scope comment in `Program.cs:187-190` matches the deployment. ⚠️ Two caveats:
- `fwd.KnownNetworks.Clear(); fwd.KnownProxies.Clear();` (`Program.cs:195-196`) means forwarded headers are honoured from **any** peer. In prod the API container is unpublished (Caddy-only entry, `docker-compose.prod.yml` service note) and `ForwardLimit` defaults to 1, so Caddy's appended rightmost value (the real client) is what's consumed — a client-sent `X-Forwarded-For: fake` becomes `fake, real` and the `fake` is never reached. OK in prod. But in **dev** the API is published on :8090 (`just up`), where a direct client's `X-Forwarded-For: fake` *is* applied — the `login-ip` floor (and `meta`, `signup`, …) can be rotated around freely on the dev box. Pre-existing config, not introduced by this commit. Follow-up F4: restrict `KnownProxies` to the compose network in prod, or accept and document dev-only spoofability.
- Stale comment: `Program.cs:368-370` still says login "is guarded by the per-IP `signup` rate limit" — it is now `login-ip` + lockout. Spec §3.5 asked for exactly this comment to be updated; it wasn't. F5.

### 2.2 Findings — rate limiting (`login-ip`)

- 60 req/min/IP fixed window, `QueueLimit = 0`, partition on `ClientIp` (`RateLimitingExtensions.cs:136-144`) — exactly the §12 flood floor; the old body-parsing `password-login` policy (which double-read the request body synchronously) is fully removed. The removal also eliminates a minor pre-existing hazard (blocking `ReadToEndAsync().GetAwaiter().GetResult()` inside the partitioner).
- Rejection is 429 + `Retry-After` from lease metadata (`RateLimitingExtensions.cs:31-38`) — consistent with the lockout's 429 shape, so the widget/dashboard see one failure grammar.
- Note (accepted risk, inherent to §12's design): anyone who knows a victim's e-mail can lock their login for 15 min with 10 unauthenticated requests (no IP exemption for successful-password-but-locked, because the check runs before password verification). The spec accepts this; flagging so it's a *known* trade-off, not a surprise.

## 3. Commit `b3160c2` — Observability Baseline (R5-58)

### 3.1 Findings — request-id middleware

**Q: does it trust a client-supplied `X-Request-Id` without length/charset validation?**
It does trust it: any non-whitespace incoming value is echoed into the response header and pushed as the `RequestId` log scope (`API/Middleware/RequestIdMiddleware.cs:30-40`). Impact assessment:
- **Log injection:** neutralised in practice — the JSON console formatter JSON-encodes all scope/state values, so CRLF/control bytes land escaped, not as forged lines. (The `RequestIdMiddleware_GeneratesIdWhenMissing` test even pins the generated format to `^[0-9a-f]{32}$` — but only for the *generated* path, `Tests/ObservabilityTests.cs:33-43`.)
- **Header size / log bloat:** Kestrel caps total request headers at ~32 KB by default, so a ~30 KB request id would be echoed on the response and copied into **every JSON log line for that request** (scope values repeat per line, `ObservabilityExtensions.cs:18-23` with `IncludeScopes = true`) — a cheap log-volume amplifier, and correlation poisoning (attacker pins their id onto victim-visible logs).
- **Response splitting via echo:** not reachable — Kestrel rejects malformed header values at parse time and `Response.Headers[...]` rejects control chars by throwing.
**Fix (concrete),** `RequestIdMiddleware.cs:33-38`: accept incoming only if `Regex.IsMatch(value, "^[A-Za-z0-9._-]{8,64}$")` (or `length <= 64 && charset ⊆ [A-Za-z0-9-_]`), else generate the GUID — one guard clause, plus a test mirroring `EchoesIncomingId` with a hostile value. Follow-up F6 (defense-in-depth; no exploitable injection found).

### 3.2 Findings — JSON logs & PII

The scope carries only `RequestId`, `UserId` (JWT `sub` → GUID) and `TenantId` (OwnerId GUID) (`RequestIdMiddleware.cs:44-74`) — no e-mail, no tokens, no bodies. The global exception handler logs method/path only (`API/Program.cs:245-246`), and `/api/uploads/file` signatures live in the query string, which is **not** logged. ⚠️ However, the switch to `IncludeScopes = true` JSON logging now permanently ships pre-existing log statements that contain recipient e-mails: `Infrastructure/Email/BrevoEmailSender.cs` logs `{To}` (three sites, including a `{Body}` on failure) and `Infrastructure/Email/SmtpEmailSender.cs` logs `{To}`. That's PII in stdout logs (and Sentry breadcrumbs — see §3.3). Not introduced by this commit, but this commit is the moment it became structured-and-shipped. Follow-up F7: redact to a hash/local-part, or route through a scrubbing formatter.

### 3.3 Findings — /health, UptimePingService, Sentry

**`/health`** (`API/Program.cs:456-476`): anonymous + `RequireRateLimiting("meta")` (120/min/IP, `RateLimitingExtensions.cs:99-107`) — both wired as spec'd; the endpoint sits after `UseRateLimiter()` (`:381`) so the metadata applies. The DB check is `AddDbContextCheck<AppDbContext>` (`API/Extensions/ObservabilityExtensions.cs:29-32`) — a `SELECT 1`-class roundtrip, no schema/table names, no connection string. What it *does* reveal anonymously: that a dependency named `"db"` exists, its health, and its latency in ms (`:468-473`). Mild footprinting; the shape is spec-mandated (R5-58 §3.3 shows the identical writer). Timing: one indexed ping per request, rate-capped — fine. Follow-up F8 (optional): emit `{"status"}` only, and gate `checks[]` behind a query-secret or dev environment, if this endpoint is ever fronted more publicly than Caddy.

**`UptimePingService`** (`API/Hosted/UptimePingService.cs`): does not hammer — the external `UPTIME_PING_URL` is hit only when local `/health` returned 2xx (`:55-62`), one tick per 60 s with a 10 s client timeout (`:50-52`); when unhealthy or erroring it logs a **status code only** (no bodies, no URLs) and skips/retries next tick (`:56-60, :73-77`). Exceptions are caught so the hosted service can't crash-loop the process (`:66-77`); the disabled path exits before any timer when the env var is unset (`:30-36`). The local URL `http://localhost:8080/health` matches the container's `ASPNETCORE_URLS=http://0.0.0.0:8080` (`Dockerfile:3`, `docker-compose.prod.yml:24`) — it does not traverse Caddy, so no ping-through-proxy amplification. ✅ Minor: `LogWarning(ex, ...)` (`:76`) can surface exception text into logs/Sentry — generic HttpClient messages, no secrets observed. ✅

**Sentry** (`API/Extensions/ObservabilityExtensions.cs:39-58`): only initialised when `SENTRY_DSN` is non-empty (true no-op otherwise — verified by test `ObservabilityTests.cs:129-137`), `SendDefaultPii = false` ✅, `TracesSampleRate = 0.1`. ⚠️ No `BeforeSend` scrub. `SendDefaultPii=false` covers SDK-added PII (cookies, IPs, user context); it does **not** scrub e-mail addresses the *application itself* put into log messages — and this repo logs `{To}` (see §3.2), which Sentry's logging integration forwards as breadcrumbs/events. So with a DSN set, recipient e-mails can reach Sentry despite the flag. Follow-up F7 (same fix): scrub/redact at the source, or add `BeforeSend` stripping `@`-containing strings from messages/breadcrumbs.

## 4. Client-Facing Behaviour Changes (widget / CLI)

- **Widget (`<pointer-feedback>`) — password login via the modal can now get 429/"locked".** The widget calls `POST /api/auth/login` (`web-component/src/element.ts:920-926`) and the handler parses the envelope regardless of HTTP status (`web-component/src/auth-ui.ts:78-81`); an unknown `status: "locked"` falls into the generic branch and shows `envelope.message` ("Too many failed login attempts…", `MessageKeys.Auth.TooManyAttempts`) — graceful, no JS error, no break (`auth-ui.ts:106-108`). It does not surface the `Retry-After`/seconds hint; cosmetic gap only. The old `password-login` 10-requests/15-min cap (which could 429 *successful* widget sign-ins — the bug §12 was written to fix) is gone. Net: widget behaviour improves.
- **CLI:** `pointer login` uses the device-code flow and `/api/auth/login-with-key` only (`cli/src/auth.ts`, `cli/src/commands/login.ts`, `doctor.ts`) — untouched by both commits; `login-with-key`'s `login` policy (`AuthController.cs:58-59`) predates this work. No change.
- **New anonymous surface:** `GET /health` (rate-limited, JSON, minimal) — plus `deploy-api.sh` now smoke-tests it (fails the deploy if the DB is down — intended).
- **All responses** now carry `X-Request-Id` (echoed if client-supplied) — inert for widget/CLI.
- **`Result` envelope grew everywhere:** `IsLocked` + `RetryAfterSeconds` (`Application/Response/Result.cs:23-29, 36-41`) and `LoginResponse.Status` documents a new `"locked"` value — serialized on **every** API response. ⚠️ Neither commit regenerated the Orval client (`git show --name-only` for both: no `clients/` paths) — violates the repo's own AGENTS.md rule ("if you change endpoints or DTOs, regenerate the client"). Follow-up F1. Same for the new `429` `ProducesResponseType` (`AuthController.cs:24`) — the typed React client currently doesn't know the locked shape.
- **Dashboard (separate repo):** should branch on `status === "locked"` / 429 to show the retry hint; the dashboard's own e2e sign-ins no longer 429 after ten successes (the §12 motivating bug).

## 5. Verdicts

### `6ca148b` (login lockout) — **MUST FIX**

| # | Severity | Finding | Evidence |
|---|---|---|---|
| M1 | **High (must fix)** | Unbounded e-mail length → unbounded `IMemoryCache` key size → anonymous remote memory-DoS (multi-GB steady state from one IP at ~10 MB/e-mail; no `SizeLimit`, no `MaximumLength`, no `[RequestSizeLimit]` on login) | `Application/Validators/LoginValidator.cs:10-12`; `Infrastructure/Auth/LoginAttemptLimiter.cs:100-101,120`; `API/Extensions/AuthenticationExtensions.cs:35` |

Fix is three lines (validator cap + hashed cache key + optional body-size limit) — after that the design itself is sound: normalisation is consistent end-to-end, unknown e-mails count, reset precedes token issuance, `Retry-After` is real, and the lock can't be extended by racing requests.

### `b3160c2` (observability) — **SAFE WITH FOLLOW-UPS**

No must-fix. The request-id echo is unvalidated but JSON-encoding + Kestrel's header limits contain it; `/health` reveals only dependency name/status/latency behind a rate limit, exactly as the spec chose; the uptime service fails closed and quiet; Sentry is PII-off by default. Follow-ups below.
