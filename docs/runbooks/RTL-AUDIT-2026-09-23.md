## 6. E-mail templates

**Finding: no Arabic e-mail content exists at all.** Every subject/body is an inline English C# string; there is no template file, no locale selection, and `EmailService.SendAsync` (`Application/Services/Implementation/EmailService.cs:19`) takes a prebuilt `htmlBody`. Sends found: `InviteService.cs:228,933,1211`; `AuthService.cs:88,186`; `UserService.cs:203,238` (`SafeSendAsync` `:54-56`); `SuggestionService.cs:375`; `DemoService.cs:216`.

A minimal RTL e-mail wrapper would need (all currently absent):

1. `dir="rtl" lang="ar"` on the outermost `<div>` (e-mail clients ignore `<html>` attributes from partial HTML, so the wrapper div must carry them).
2. Logical inline styles: `text-align: start`, `padding-inline-start`, `margin-inline-end` — or duplicated `[dir]`-conditional rules, since Outlook/WebView clients have uneven logical-property support.
3. RTL-safe arrow: `&rarr;` (`AuthService.cs:94`, `UserService.cs:208`) reads backwards in RTL — use `&larr;` for ar or a neutral glyph.
4. Bidi isolation for interpolated values: workspace names/product names inside Arabic sentences need `<bdi>` (or `direction: ltr; unicode-bidi: embed` spans) so mixed Latin names don't scramble.
5. A locale decision upstream: recipients have no language preference today (`User` has none consumed here) — needs a per-user language column or workspace default before any translation is possible.

Localization itself is ticketed out of scope by the roadmap doc (§2, §10); the wrapper spec above is what the fix ticket should contain.
