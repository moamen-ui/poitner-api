| Severity | Finding | Evidence file:line | Suggested Fix |
| :--- | :--- | :--- | :--- |
| **BLOCKER** | **Cross-tenant data exposure during impersonation.** The `User` filter unconditionally returns true if `currentUser.IsSuperAdmin`. Since `JwtTokenService` injects `is_super_admin=true` into impersonation tokens, an operator impersonating Workspace A will bypass the `Memberships` check and see **all** users across all tenants. This bug exists on both `main` and the branch. | `Infrastructure/AppDbContext.cs:108` and `JwtTokenService.cs:175` | Change the bypass to `(!currentUser.IsImpersonating && currentUser.IsSuperAdmin)` so impersonators fall through to the tenant-scoped `e.Memberships.Any(...)` check. |
| **HIGH** | **Normal users cannot read their own row on Selection/MFA tokens.** A user authenticating with a selection token has `TenantId=null` and `IsSuperAdmin=false`. On the branch, the no-tenant fallback strictly requires `r.IsSuperAdmin == true`. Normal users will fail to load their own profile (e.g., for an avatar in the workspace selector UI) unless the endpoint uses `IgnoreQueryFilters()`. | `Infrastructure/AppDbContext.cs:116` | If endpoints like `/api/users/me` don't use `IgnoreQueryFilters()` (unlike login), add `\|\| e.Id == currentUser.Id` to the no-tenant branch to let users read their own row. |
| **MEDIUM** | **Missing index on `User.RoleId` causes full table scans.** To evaluate the no-tenant branch, PostgreSQL must scan `Users` and execute a PK lookup on `Roles` for every row. Without a foreign-key index on `User.RoleId`, any query asking for super-admins will result in a sequential scan of the entire `Users` table. | `Infrastructure/AppDbContext.cs:116` | Add an index on `RoleId` in the `User` entity configuration to allow PostgreSQL to filter the table efficiently via a hash join or index scan. |
| **LOW (Info)** | **Tenant-owned roles cannot spoof super-admin access.** Using `Set<Role>()` invokes the `Role` query filter. If a tenant creates a local role with `IsSuperAdmin=true`, the injected `Role` filter enforces `r.OwnerId == null` for a no-tenant caller, brilliantly hiding the spoofed role. | `Infrastructure/AppDbContext.cs:116` | No fix needed. This is an elegant security benefit of the `Set<Role>()` approach. |
| **LOW (Info)** | **Nullable RoleId correctly handled.** If a user's `RoleId` is null, the subquery safely evaluates `r.Id == null` to false, correctly excluding them from the platform-admin bucket. | `Infrastructure/AppDbContext.cs:116` | No fix needed. |
| **LOW (Info)** | **Super Admins at Login.** As noted in your comments, login uses `IgnoreQueryFilters()`. Therefore, the Role filter hiding logic does not prevent super admins from loading their own row during initial authentication. | `Infrastructure/AppDbContext.cs:118` | No fix needed. |
