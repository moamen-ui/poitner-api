## DB-12 — audit log

1. **Major — build-breaking omission: the R8.5 reflection test is not amended.**
   `Tests/WorkspaceTests.cs:305-313` fails for *any* Domain type with an `OwnerId` property that is neither in
   `TenantService.HardDeleteOrder` nor excluded by name; `:312` excludes only `Workspace` and `UsageEvent`, and
   `:323` pins `HardDeleteOrder.Length == 22`. `AuditEvent` (§3.1) carries `OwnerId` and is deliberately not a
   `BaseEntity` — exactly the `UsageEvent` trap. §4 says the exemption applies and §2 cites the test, but **no task
   in §5 and no test in §6 edits `WorkspaceTests.cs`**, so a literal implementer finishes task 14 and `just test`
   fails with "Type(s) not covered by TenantService.HardDeleteOrder: AuditEvent". DB-13 (task 2) and DB-15 (task 2)
   both remember this edit; DB-12 forgot its own. **Change:** add to §5 task 3: *"`Tests/WorkspaceTests.cs:311-312` →
   `&& t != typeof(AuditEvent)` with the comment `// operator record: FK SET NULL, survives the workspace (DB-12, R8.8)`"*,
   and add a §6 assertion that the exclusion list is exactly `Workspace, UsageEvent, AuditEvent`.
2. **Major — the `Audit:StrictCoverage` 500 rewrite is not implementable as specified.**
   §3.8 has `AuditCoverageFilter : IAsyncActionFilter` "after `await next()` … rewrite the response to
   `500 Result.Failure("Audit gap")`". In ASP.NET Core, `await next()` for an action filter includes MVC's result
   execution — the 200 body has been written and `Response.HasStarted` is true; setting the status code/body then
   throws `InvalidOperationException` (headers read-only / response started). A mid-tier implementer will discover
   this only at e2e time and improviate. **Change:** keep the gap *detection* in the action filter (set
   `Items["audit.gap"]`, log), but perform the strict rewrite in an `IAsyncResultFilter.OnResultExecuting` that
   replaces `ctx.Result` with `new ObjectResult(Result.Failure("Audit gap")) { StatusCode = 500 }` when the item is
   set — or throw before result execution. Amend §3.8/§5 task 9/§6 test 7 accordingly.
3. **Major (cross-doc, breaks DB-13's D13.6 promise) — the audit read API leaks the operator's identity to the workspace admin.**
   DB-13 §3.8 D13.6: "Is the operator's identity shown to the workspace? **No** — … `operator_user_id` is visible
   to super admins only". But DB-12 §3.6 reserves `impersonation.started`/`.ended` rows written with
   `OwnerId = the impersonated workspace`, `actor_kind = Impersonation`, `actor_user_id = sub` (the operator's
   `public_id`), and §5 task 12's `AuditEventDto` exposes `ActorUserId` **and** `ActorName` (`UserNameResolver`)
   in the workspace view (`GET /api/admin/audit`, owner-filtered). The workspace admin's Security log would render
   the operator's display name. **Change (either doc, whichever lands second):** in `AuditQueryService`, when
   `ActorKind == AuditActorKind.Impersonation` and the caller is not a super admin, emit `ActorUserId = null` and
   `ActorName = "Operator"`; keep both in the `/all` view. Add a §6 test: workspace admin's view of an
   `impersonation.started` row shows no operator uuid/name.
4. **Minor — the trigger's permitted UPDATE cannot be attributed to the FK; say so.**
   The exemption is "shape-based": *any* `UPDATE audit_events SET owner_id = NULL …` with every other column equal
   passes, not only the one the FK's `ON DELETE SET NULL` generates. An operator with SQL access can silently
   detach rows from a workspace by hand and the trigger cannot tell. This is inherent (Postgres gives the trigger
   no reliable "I am a referential action" signal; `pg_trigger_depth()` does not distinguish it) and acceptable —
   but §3.2/R17 wording ("the single permitted UPDATE **is** the FK's") overclaims. **Change:** one sentence in
   §3.2: *"the trigger admits the FK action's shape (`owner_id` → NULL, byte-identical otherwise) — it cannot
   attribute the UPDATE to the FK; a manual detach of that exact shape is equally permitted and only the release
   log/psql history would show it."* No code change.
5. **Minor — the workspace audit view 403s an impersonating operator.**
   §5 task 12 gates `ListForWorkspaceAsync` on `TenantStamp.TryRequireOwner`, which is false for super admins
   (S-14, and unchanged under impersonation — the §3.3 token has `is_super_admin=true`). A DB-13 session therefore
   cannot read the target's own security log mid-session, while it *can* read the content. DB-15 §3.5 already
   handles this exact case for its activation endpoint ("`TryRequireOwner` false → use `TenantId` when
   `IsImpersonating`"). **Change:** add the same branch to `AuditQueryService.ListForWorkspaceAsync` (or state
   that the impersonating operator must use `/all`).

**Verified correct (for the record):** the trigger SQL is valid PostgreSQL — `to_jsonb(record)` in a plpgsql
trigger, `- 'owner_id'` key removal, jsonb equality is semantic and stable within a statement (FK SET NULL touches
only `owner_id`, so both sides are identical); referential-action UPDATEs fire BEFORE UPDATE row triggers, which
is why the exemption works; `BEFORE TRUNCATE … FOR EACH STATEMENT` with `TG_OP='TRUNCATE'` reaching the RAISE is
correct; `USING ERRCODE 'restrict_violation'` (23001) is valid; one multi-statement `migrationBuilder.Sql` with
`$$`-quoting and no parameters is fine on Npgsql inside the migration transaction. The DB-02 guard
(`Tests/MigrationSafetyTests.cs:75-82`) flags `.Sql(` and accepts the proposed `R4 constraint approved … by Moamen`
marker (`\S+` matches "Moamen"); Migration 1 carries no `.Sql(`. `SaveChangesAsync` at `AppDbContext.cs:304-334`
loops `Entries<BaseEntity>()` only, so the pre-loop `AuditEvent` guard is correctly placed. R8.8, R10 reserved
strings, R11 probe warnings ("never run on production"), R7.1 batching notes — all consistent with DB-RULES.

**Verdict: needs edits** — (1) WorkspaceTests exclusion task, (2) StrictCoverage rewrite mechanism, (3)
operator-identity redaction in the workspace audit view (with DB-13), plus minors 4–5. Safe to implement after
those; nothing here should reopen design.

   `ExportImportService`: add `ExportWorkspaceAsync → Forbidden(MessageKeys.Impersonation.Required)` when
   `IsSuperAdmin && !IsImpersonating` (mirroring `ListAllRulesAsync`), or accept and document.
4. **Minor — one-live-session-per-operator is code-only.** Two concurrent `Start` calls race past the
   `AlreadyActive` check; harmless (both rows audited, both tokens work) but §3.6 should either accept it in
   words or add `ux_impersonation_sessions_operator_live` as a **unique** partial index (same DDL cost, since the
   index already exists as non-unique).

## DB-15 — activation funnel & usage rollup

1. **Minor — `RetentionService.BindOptions()` is not named.** `RetentionOptions.RollupDays` (§3.4) is bound via
   `BindOptions()` (`RetentionService.cs:66-77`, verified), which constructs the record field-by-field — a literal
   implementer who adds the property and the appsettings keys but not the `BindOptions` line silently loses the
   env override (`RETENTION_ROLLUP_DAYS` ignored, default 3 always). **Change:** task 6: "`BindOptions()` gains
   `RollupDays = config.GetValue("Retention:RollupDays", 3)`".
2. **Minor — NULL-owner grouping in the weekly number is specified only for `demo_started`.** §3.1 defines
   workspace semantics per step, and §6 covers `Funnel_HardDeletedDemo_StillCountedAsStarted`, but the
   `date_trunc('week', min(created_at)) GROUP BY owner_id` sketch merges **all** hard-deleted (owner-NULL)
   workspaces into one pseudo-workspace for `workspace_converted`/`first_apply` as well. The in-memory
   implementation should state the rule once: "a row with `OwnerId = NULL` counts toward the step total (the
   workspace existed) and toward its week via the row's own `created_at`; it never merges with another NULL-owner
   row." One sentence in §3.1 removes the ambiguity a mid-tier model would otherwise resolve by accident.
3. **Minor — the failure-injection test prescribes an exception the spec never requires.** §6 test 2
   (`Sweep_SkipsUsageDeleteWhenRollupFails`) drives `RollupDays = -1` and expects
   `ArgumentOutOfRangeException`; §3.4's algorithm never says `RollupAsync` validates its arguments. **Change:**
   add to §3.4: "`if (o.RollupDays < 0 || o.UsageEventsDays < 0) throw new ArgumentOutOfRangeException` (the
   test's failure-injection seam)". Otherwise the implementer writes a loop that simply processes no days and the
   test cannot be written as specified.
4. **Minor — `widget_installed` is forgeable by anyone, accept it in words.** The emission sits on the anonymous
   `widget-status` endpoint (`WidgetPublicController.cs:14-23`, verified anonymous + origin-forwarded), so an
   unauthenticated caller can mint the one-shot fact for any active project from any non-localhost origin (e.g.
   `curl -H 'Origin: https://x.example'`), inflating "widget installed". Not a security issue (the row carries
   only an origin string ≤ 2000 chars, R12-capped; no PII). D15.2's definition is what it is — pre-launch, with
   one real workspace, the distortion risk is ~zero; say so in §3.2 so nobody discovers it as a "bug" later.

## Cross-cutting answers (concise)

- **DB-12 trigger correctness:** valid PostgreSQL; the `to_jsonb(NEW) - 'owner_id' = to_jsonb(OLD) - 'owner_id'`
  comparison is semantic jsonb equality (stable within a statement), FK `ON DELETE SET NULL` fires the BEFORE
  UPDATE row trigger, TRUNCATE is covered by the statement trigger, ERRCODE/marker/`[ContractMigration]` all
  satisfy the DB-02/DB-09 machinery. One honest caveat (DB-12 §4): the exemption is shape-based, not
  FK-attributed — see finding 4.

  DB-13 §3.4 and I verified each against code (see DB-13 section); the three that *would* have gone empty
  (PlatformInsights comments, Stats comment counts, AiRules prompts) are explicitly patched, and export/comment
  reads 404 via `EnsureAsync` for a plain operator as claimed.
- **Impersonation token safety:** sound — read-only + exact-path end fence, hard ≤60-min expiry equal to the
  session's `ExpiresAt`, per-request fail-closed liveness, identity-stamp revocation preserved, start/end audit
  rows with a 5-min sweep for expiries, workspace e-mail at start, request counter. Residuals: the D13.6 audit-DTO
  leak (DB-12 §3), no e-mail for admin-less workspaces, code-only single-session enforcement.
- **DB-14 lockouts:** none — super admin seeded-verified + claim-skipped, addressed invites verified on accept,
  open invites/demo/stakeholders keep read+comment, gate touches only `/api/admin/*` non-GET, backfill is
  idempotent and date-bounded with a slip plan.
- **DB-15 emissions & idempotency:** server steps exist today or are added at verified save points; client steps
  match the validator exactly (CLI `first_apply` rejected, as the doc says); the rollup is idempotent by
  construction with the NULL-owner grouping ambiguity being the only unspecified corner.
- **Implementability by a mid-tier model:** all four are written to a rare standard — verified line citations,
  defaulted owner decisions, explicit test lists. The literal-implementation traps are exactly the numbered
  findings above: DB-12's reflection-test omission (build break) and StrictCoverage mechanism (impossible as
  specified), DB-14's two unlisted inline checks (its own acceptance criterion fails), DB-15's BindOptions line
  and the argument-validation seam its test prescribes. Everything else is copy-precise.
