# AGY — review of DB-12…DB-15

## DB-12 Audit Log
- **1. [Minor] PostgreSQL trigger correctness:** The trigger syntax `(to_jsonb(NEW) - 'owner_id') = (to_jsonb(OLD) - 'owner_id')` correctly strips the `owner_id` key and checks that the rest of the row is byte-identical. Because EF Core handles the `ON DELETE SET NULL` as a native PostgreSQL constraint cascade, this reliably permits only the workspace hard-delete cascade.
- **Verdict:** Safe as-is.

## DB-13 Operator Impersonation
- **1. [Blocker] Content exposure bypass in `SuggestionService`:** `SuggestionService.LoadOwnAsync` (`Application/Services/Implementation/SuggestionService.cs:327`) uses `IgnoreQueryFilters()` and drops the tenant restriction if `!_currentUser.IsSuperAdmin`. Since this returns `PredefinedActionSuggestion` (which contains stakeholder text), a plain, non-impersonating operator can call `POST /api/admin/suggestions/{id}/approve` to read and modify content. **Change:** Add `SuggestionService.LoadOwnAsync` to the DB-13 edit list, requiring refusal for non-impersonating operators.
- **2. [Major] Broken `ProfileService` counts for operators:** `ProfileService.BuildAsync` (`Application/Services/Implementation/ProfileService.cs:74,85`) aggregates `Comment` and `Reply` rows without using `IgnoreQueryFilters()`. With `IsSuperAdmin ||` removed from the global filters, an operator querying a user's profile will receive zeroes for all counts. **Change:** Add `ProfileService.BuildAsync` to the DB-13 edit list to use `IgnoreQueryFilters()` when `IsSuperAdmin` is true (matching the `PlatformInsightsService` precedent).
- **Verdict:** Needs edits (list above).

## DB-14 Email Verification & Passwords
- **1. [Blocker] Gate compilation / translation failure:** `RequireVerifiedEmailFilter` (§3.4) does `var sub = ctx.HttpContext.User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value;` and then queries `.Where(u => u.PublicId == sub)`. Since `u.PublicId` is a `Guid` and `sub` is a `string`, this will not compile or will fail EF Core translation, breaking all protected routes. **Change:** Update the spec to parse the Guid (`Guid.Parse(sub)`).
- **2. [Major] Addressed invite lockout for existing unverified users:** DB-14 §3.2 rule 12 specifies "join-or-create onto an existing identity -> unchanged". If an existing unverified user accepts an addressed invite (`invite.Email != null`), their `EmailVerifiedAt` is left as `null` and no email is sent. They become an Admin in the new workspace, hit the gate, and are stuck until they discover the manual "Resend" action. **Change:** Allow updating `EmailVerifiedAt` to `now` during a join if the invite is addressed and matches their email.
- *(Note on others: Super admin seeded from env is skipped via `is_super_admin == "true"`; Demo is skipped via `IsDemo`; grandfathering date literal logic is sound and handled via deploy-date instructions).*
- **Verdict:** Needs edits (list above).

## DB-15 Activation Funnel & Usage Rollup
- **1. [Minor] Funnel events are not emitted via `RecordEventAsync`:** The prompt asked to check `RecordEventAsync` call sites for funnel event definitions. None of the funnel events (`first_comment`, `first_apply`, `demo_started`, `workspace_converted`, `widget_installed`) are emitted via `RecordEventAsync`. That method is exclusively used by the client-facing `EventsController`, and its `RecordEventValidator` explicitly rejects the funnel event types. Instead, the server emits them directly via `_unitOfWork.UsageEvents.Add` (e.g. `CommentService.cs`). This is the correct architecture, but clarifies the question.
- **2. [Minor] Rollup idempotency:** The rollup inside `RetentionService` is idempotent. Because the sweep deletes events older than 180 days, and the rollup window only targets the recent days (e.g., `RollupDays = 7`), they do not overlap. The logic queries the DB and updates `Count` if the group exists, ensuring safe re-runs without unique constraint violations on `usage_daily`.
- **Verdict:** Safe as-is.
